# Architecture Audit — Drift, Divergence, and Redundancy

> **Audited:** 2026-08-24 · **Against:** v0.7.5 working tree (package 0.7.4)
>
> **Status: HISTORICAL NARRATIVE — do not edit, do not track work here.**
> This file is the evidence and reasoning behind each finding, kept because the
> *why* is what stops a fix being re-filed as drift. Live tracking moved out on
> 2026-08-26:
>
> - **`docs/audit-register.md`** — the tracker: every item, its state, its id.
> - **`docs/device-validation.md`** — the on-device steps each fix depends on.
>
> Five findings in this file were re-derived against the tree on 2026-08-26 and

> are recorded in "Corrections" at the foot of this document. Read that section
> before acting on §1.2, §2.8, §2.9 or register item 4b.

This is the detailed record of a three-lens adversarial review: (1) a general correctness/dead-code pass, (2) intended-design vs current-state drift, and (3) store-logic drift and redundancy. It is the source material for the remediation register at the end. The companion guard is the `unifideck-drift-guard` skill plus `scripts/validate_architecture.py`, which machine-enforce the drift classes found here.

Two facts frame every section:

1. **The code is ahead of its documentation by a full store and roughly a full release.** Battle.net is implemented but every doc and skill still says "five stores." Version strings disagree (§2.6).
2. **There is no single agreed layer model or store-type model.** Four incompatible layer maps exist, and the wrapper/CLI distinction is maintained in two separate hand-written tables with no linking field.

## Part 1 — General adversarial review

### 1.1 P0 correctness bugs (silent failures)

1. ~~**`GAME_INSTALLED` payload contract mismatch.**~~ **RESOLVED — and the original diagnosis was wrong.** The finding claimed the emitter at `core/manifest.py:463-470` sent `game_id` while both subscribers read `app_id`, killing artwork-on-install and Proton-on-install "despite the event firing". Validation showed the event **never fired at all**, and that fixing the payload would have changed no behaviour:

   - The only emit site was `_scan_one_root` inside `discover_all`, whose two wrappers (`discover_installed_games`, `discover_and_log`) had zero callers — their only references were `vulture_whitelist.py` entries. The dead code had already been noticed and silenced rather than deleted.
   - Artwork-on-install was **redundant, not missing**: a game's shortcut and its cover art are created at *sync* time, and installing only flips that shortcut's install tag while preserving its appid (`services/shortcut/events.py:163-178`). `download/worker.py` documents the same reasoning where it declines to emit.
   - Proton-on-install had **four** independent reasons it could never work: no live emitter; the payload key mismatch; `DEFAULT_TOOLS` empty for all six stores by design; and in the plugin the writer was pointed at `localconfig.vdf` (`bootstrap/paths.py:166`, re-bound by `steam/current_user.py`) while `CompatToolMapping` lives in `config/config.vdf`.
   - **The real user-facing bug was on the frontend and this audit missed it.** `src/lib/steam-bridge/collection-manager.ts` subscribed to `GAME_INSTALLED` to rebuild the `[Unifideck] Installed` collection. That never fired, while `GAME_UNINSTALLED` on the next line did — so the collection (and any TabMaster tab on it) dropped games on uninstall but never picked them up on install until the next full sync. Its own comment claimed to have fixed exactly that.
   - Both guards locked in **opposite halves** of the mismatch and so caught nothing: `tests/unit/test_proton_ge.py` asserted the subscriber's `app_id` contract while `scripts/validate_event_schemas.py` asserted the emitter's `game_id` contract.

   Fix: repointed the collection manager at `SHORTCUT_INSTALL_STATE_CHANGED` (the event that actually fires, in both directions), then deleted the phantom event and everything hanging off it — both dead subscribers, the dead discovery half of `core/manifest.py` (520→257 lines), the entire ProtonService compat-tool path (243→120 lines, resolving half of §1.4), and the two `vulture_whitelist.py` entries. `Events.GAME_INSTALLED` no longer exists, so nothing can subscribe to it again.

   **Lesson for the rest of this register:** "emitted but with the wrong payload" and "not emitted at all" look identical from a grep of emit sites. Check that the *enclosing function* has callers before trusting an emit site, and check whether a dead subscriber's job is already done elsewhere before restoring it.

2. ~~**`TOAST_NOTIFICATION` is emitted but consumed nowhere.**~~ **RESOLVED — the finding held, and the impact was larger than stated.** All three emit sites are live-reachable (checked the enclosing functions per §1.1.1's lesson): `emit_circuit_open_toast` ← `check_circuit_breaker` ← `LauncherService.launch`; `emit_launcher_error_toast` ← `handle_launcher_error` ← the same `launch`; `_emit_write_refused` ← `_save_shortcuts`'s write guard. Three independent reasons none of them ever reached a user:

   - **No consumer**, as the audit said: absent from `src/types/events.ts`, absent from `WATCHED_EVENTS`, no Python subscriber.
   - **Wrong process — the audit missed this, and it is the load-bearing half.** `LauncherService` is built *only* by `launcher/bootstrap.py:69`, the out-of-process launcher. Its bus dies with the process, and `frontend_bridge.install_bus_forwarder` mirrors `LAUNCHER_STAGE` **and nothing else** into the bridge file. Adding a frontend subscriber alone would have fixed nothing for the two launcher toasts. (`ShortcutService` is built in *both* processes — `build_service_subset` includes `"shortcut"` — so its toast needed both legs to work.)
   - **Payload key mismatch**: emitters sent `params=`, both renderers read `i18n_params`. Fixing the first two alone would have rendered `"Couldn't launch  (). Check the logs for details."` — the same class of failure as §1.1.1's `app_id`/`game_id` split.

   The i18n strings existed and were translated in all 16 locales the whole time; only the delivery channel was dead.

   **What the user actually experienced.** A circuit-breaker refusal was *completely* silent: the toast was dead, and `CIRCUIT_STATE_CHANGED` sits in `WATCHED_EVENTS` with zero frontend subscribers (the `useCircuitState` hook and `PlayButtonOverride` badge its docstring describes were never built), and `clear_launch_failures` / `arm_circuit_bypass` have no frontend caller (§1.2). So after 3 failures in 10 minutes the user pressed Play, got a flicker, landed back on the game page with no message, no badge, and no way to reset — reading as "the plugin randomly stopped launching my game." Terminal `LauncherError`s were equally silent (the dispatcher maps the `Result` to an exit code and exits; Steam shows nothing for a non-Steam shortcut exiting non-zero). And a shortcut write refusal left the sync reporting success while the library silently did not change — the exact silence `_emit_write_refused`'s docstring exists to prevent.

   Fix: routed all three through `LAUNCHER_STAGE` — the one channel wired on both delivery legs — then deleted `Events.TOAST_NOTIFICATION` so nothing can emit into it again, along with its `validate_event_schemas.py` row and its arm of `check_hardcoded_strings.py`'s `PY_BUS_EMIT` regex. Added `duration_ms` to `emit_stage`/`launcher_toast` and taught both renderers to honour it via a shared `src/services/toast-duration.ts` (the write-refusal paragraph asks for 12s and was being cut at 7.5s). The two launcher toasts now name the game via the existing `launcher/game_title.resolve_title`, fed into the `{{game_key}}` placeholder the strings already declare — zero locale churn. Dropped the "Show logs" action (see the new register items) and with it `circuit_breaker.get_launch_id_or_none`, whose only purpose was to build it. New `tests/unit/test_toast_channel_migration.py` asserts each emitter against the **consumer's** contract, not the emitter's.

3. ~~**`MetricsCollector` timers/gauges are never wired.**~~ **RESOLVED before this register was worked, by commit `8b62be5`** ("use @subscribe decorators for metrics…"). The finding was accurate: `auto_wire(self, self._bus)` and its `logger.info` sat inside the `for event, name in counter_events:` loop (confirmed at `8b62be5^:core/metrics_collector.py:96-100`), so they ran 7 times, and the timer/gauge `_on_*` handlers carried no `@subscribe` metadata. Verified fixed in the current tree: `auto_wire` runs once outside the loop (`metrics_collector.py:104`) and every `_on_*` handler is decorated. `tests/unit/test_metrics_collector.py` pins both halves. The register line was simply never ticked.

4. ~~**Double emission of `DOWNLOAD_*` with incompatible payloads.**~~ **RESOLVED — and the audit named the wrong symptom.** The mechanism was as described: for Epic/Amazon every phase emitted twice, once in the `DownloadWorker` shape (`item=`, plus `game=` on completion) and once in a flat store shape (`store=`, `game_id=`) from `epic/install.py` and `amazon/amazon_install.py`. Ten emit sites in all — 4 in Epic, 6 in Amazon. Validation changed the impact story:

   - **The audit's stated impact was half wrong.** It said "the game-info refresh silently no-ops". The store-shaped `DOWNLOAD_COMPLETE` does have no `game`, so `extractAppId` returns `null` and *that event's* `invalidateGameInfo` / `bumpGameStateVersion` / `invalidateGameSize` are skipped — but the worker's later event carries `game` and does the refresh. Nothing was lost; it cost one wasted `get_download_queue` round-trip.
   - **The real user-facing symptom was a duplicate failure toast, and this audit missed it.** `download-store.ts:onFailed` toasts on *every* `download_failed`. A failed Epic or Amazon install produced two: the store-shaped one first, with no game name (it had no `item.game_title`) and then the worker's, titled. Same body from `friendlyDownloadError`, 7.5s each. GOG, Ubisoft and Battle.net showed one.
   - **The store-shaped completion also fired early.** Epic emitted it in `_finalize_install`, *before* the worker ran prefix warmup — allowed 600s. Nothing consumed it that way, but that is the exact shape of a bug this repo has already had: `launcher/wrapper_prefix_probe.py:22` records Battle.net installs dying with `GameNotFoundError` because a "premature `DOWNLOAD_COMPLETE` wrote a `games.map` row".
   - **The counters that ship in support bundles read double for two of six stores.** `download_completed` / `download_failed` incremented twice per Epic/Amazon install (`rpc/mixins/observability.py:214` folds `plugin_metrics` into the bundle at `environment.json` → `frontend.plugin_metrics.counters`).
   - **`services/shortcut/events.py:_on_download_complete` was one guard away from acting on the bad payload.** Its `isinstance(game, Game)` check is the only reason a store-shaped completion didn't reach `mark_installed` with no game — the same silent-no-op class as item #1.

   Fix: deleted all ten store-installer emits (`_fail` in Epic is now a pure `InstallResult` builder), and unified the one remaining shape — `DownloadWorker._update_progress` now emits `item=item.to_dict()` instead of flat `store`/`game_id`/`progress`/`speed_mbps`/`eta_seconds`, so all five `DOWNLOAD_*` events carry the queue item. That let the frontend key progress by row id (`mergeProgressIntoSnapshot`) instead of writing every tick onto whatever row was on screen, and carries `download_phase`/`phase_message` on the tick rather than on the next refetch.

   Three defects found while tracing this one, all fixed here because they live in the same payload path:

   - **`download_duration_ms` measured the wrong window.** `_run_prefix_warmup` re-emits `DOWNLOAD_STARTED` to push the "preparing" phase to the frontend, and `_on_download_start` *assigned* the pending start time — so the recorded duration was the warmup span, not the install. True for GOG too, so not caused by the double emission, just hidden behind it. Now `setdefault`: the first start wins.
   - **A cancelled install leaked a `_pending_timers` entry for the plugin's lifetime.** Metrics subscribed to `DOWNLOAD_FAILED` but not `DOWNLOAD_CANCELLED`, while `test_failed_download_drops_the_pending_timer` called this out as "the leak that mattered" with the cancel half still open. These two are **one** fix, not two: `setdefault` is only safe because all three terminal events now clear the entry — otherwise a retry inherits the abandoned attempt's clock.
   - **The frontend wrote every progress tick onto `queue.current`** regardless of which game the event described. Dormant only because `DownloadService`'s `max_concurrent` defaults to 1. `mergeProgressIntoSnapshot` now matches on `item.id` and returns the previous snapshot object unchanged on a miss, so a non-matching tick costs no re-render either.

   Guard: `CANONICAL_SCHEMA` in `scripts/validate_event_schemas.py` is narrowed to the post-fix kwargs, and a new `EMITTER_OWNERS` check asserts `DOWNLOAD_*` is only emitted from `services/download/`. The narrowed schema catches a duplicate that invents its own payload; the ownership check catches one that copies the right payload from the wrong place. Both were verified to fail the gate against a deliberately-planted violation, not just to pass against the clean tree.

   **Lesson for the rest of this register:** the mechanism can be right while the named consequence is wrong. Two emitters were real, but the consequence the audit predicted (a lost refresh) was absorbed by the duplicate, and the consequence it didn't predict (a doubled toast) was the one users saw. Trace what each *consumer* does with each payload before writing down the impact.

### 1.2 Dead RPC methods (implemented, zero frontend callers)

~~Roughly 13 implemented methods have no caller.~~ **RESOLVED — and both of this section's own lists were undercounts of the same thing.** The two lists are disjoint: the 14 named here and the 15 the validator reported were different methods, and nobody added them up. The real figure was **29 of 102 mixin RPC methods, 28% of the surface.** Re-derived by cross-referencing public `async def` on `*Mixin` classes (the surface `@auto_wrap_rpc_methods` exposes) against every `.ts`/`.tsx` for both the snake_case name and `rpcRoutes.<camelCase>`; every remaining textual hit was read and all were comments, docstrings or one test fixture string. No dynamic route composition exists (`rpcRoutes[...]` indexing appears nowhere), so there was no hidden caller path.

Two structural causes, not 29 independent oversights:

- **A phantom UI.** "DiagnosticsPanel" is named in six backend docstrings (`probe_reaction_service.py:9`, `security/audit_log.py:8`, `security/config.py:72`, `security/auth.py:72`, `security/redaction.py:12`, `bootstrap/boot.py:153`) and has never existed in `src/`. Eleven RPCs were its backend half. `main.py:167` called the config-validation result "shown in the UI"; `boot.py:153` told the user they "can still see the DiagnosticsPanel and fix their config". Neither was true.
- **Superseded routes were never removed.** Six methods had been replaced by a better route — a bulk sweep, a display variant, the support bundle — and left declared in `rpc-routes.ts`.

**Why the guard missed 14 of them.** `find_dead_rpc` asked only "does this snake_case name appear anywhere in `src/` text". A method declared in `rpcRoutes` whose constant nothing references passes that test, because the route table itself keeps the name present. That is the whole gap, and closing it was the highest-value part of the fix.

**Three were dead wrappers over very live functions** — per §1.1.1's lesson, the wrapper went and the function stayed: `save_proton_setting` (live at `compatibility/proton_helpers.py:309`, called by `prefix_setup.py:183` and `ge_fallback.py:105`), `is_edge_installed` (live at `auth/edge_browser/detection.py:126`), `get_plugin_metrics` (live at `core/metrics_collector.py:120`, folded into the support bundle).

**Runtime proof before deletion.** A throwaway one-line probe in `rpc_wrapper` logged every RPC invocation — all 102, so it validated the analysis in both directions. Across a full exercise (boot in Desktop Mode, QAM, library sync, five App-Details opens, two game launches, updater modal, Capture Logs, store sign-out/in) **34 of the 73 live methods fired and none of the 29 suspects did.** The remaining 39 live methods sit on paths not exercised (installs, cloud-save push/pull, per-store auth contexts); `get_compat_tool_for_game` in particular is conditionally live on the Ubisoft/Battle.net launch path only. This step is what §1.1.1 says to do and it is cheap; it should precede any future deletion pass.

**What the user actually experienced.** For 26 of the 29, nothing — they were unreachable code, and deleting them changed no behaviour. Three were real:

- **Cloud-save failure toasts could not be silenced.** `cloud.failure_behavior.<store>` is read live at launch (`launcher/cloud/cloud_failure.py:133-141,161`) and defaults to `"toast"`, so a store whose cloud sync fails toasted on every launch of that game with no way to turn it off. The setting worked; only its UI was missing. **Decided: current behaviour is acceptable**, so the two RPCs were deleted rather than wired — the config key stays hand-editable.
- **A malformed user config was completely silent.** `validate_config_at_startup` set `_config_validation_result`, set `_config_degraded`, and emitted `CONFIG_VALIDATION_FAILED` — and all three landed in dead ends: the result was read only by the dead `get_config_validation_status`; `_config_degraded` was **written and never read anywhere**, so "degraded mode" had no behaviour at all; and the event fed SecurityService's audit log, readable only through five dead RPCs. Typo a key in `~/.config/unifideck/config.json` and you got one log line.
- **The circuit-breaker / launch-log / save-folder trio** was already register 4a/4b. Five of the 29 are their RPC halves, so they are resolved there, not twice.

**Cost to support rather than to users.** The support bundle is how reports actually arrive, and it carried no bus health, no security timeline and no config-validation result. Worse, `_support_bundle_extra` *promised* `runtime_probes` while delivering nothing (its only writer was the uncalled `report_runtime_probes`) and promised `plugin_metrics` while delivering empty timers/gauges (register #2).

Fix, in two passes. **Phase 1** deleted 12 superseded or unwanted routes, each against a verified live replacement: `get_sync_status` (an exact alias of `get_sync_progress` — both are `return self.sync_service.get_status()`), `check_game_update`, `get_game_metadata`, `get_release_notes`, `export_launch_logs`, `is_edge_installed`, `save_proton_setting`, `get_all_playtimes`, `sync_playtime_now`, `inject_hide_css`, and the two `cloud_failure` routes. `inject_hide_css` was the only reachable path into `cdp/cdp_inject.py`, so that module went too (166 lines; its `create_cef_debugging_flag` re-export had always resolved to `None` because `cdp_utils` has never existed on disk). `get_available_updates` was rerouted through `_request_update_scan`, which `check_game_update`'s deletion had orphaned, removing a duplicated sweep-refresh.

**Phase 2** took the DiagnosticsPanel cluster. Rather than delete the signal with the route, three snapshots moved into `_support_bundle_extra` — the delivery channel that demonstrably works — and then all 12 routes went: the five `security` methods, `get_bus_health` (body demoted to a private `_bus_health` collector), `get_probe_history`, `get_feature_flags`, `get_config_validation_status`, `get_plugin_metrics`, `release_quarantine`, `report_runtime_probes`. `SecurityRPCMixin`, `ConfigValidationRPCMixin` and `CloudFailureRPCMixin` emptied out entirely and were deleted; the mixin count went 20 → 17.

**The fold needed one real fix, not just a test.** `ValidationError.message` is `err.message[:256]` straight from jsonschema (`config/validator.py:423`), and jsonschema interpolates the offending *instance* — a bad `stores.*.client_id` renders as `"'sk-abc123' is not of type 'integer'"`. `scrub.py` is key-based and cannot catch a value embedded in a message string, so folding the raw error list into a bundle people paste in public would have leaked config values. Added a `safe_message` field built from `err.validator` + `err.validator_value` (both schema-side, e.g. `"type != integer"`); the bundle carries `{source, path, safe_message}` and `message` stays log-only. The security audit log needed no such work: `audit_emitter._emit` already runs `redact_for_audit` *before* `bus.emit` (`security/audit_emitter.py:92`), so `AuditLog.record` only ever stores redacted payloads — note the guarantee lives in the emitter, not in `record`, which stores `dict(payload)` raw.

**One planned fold was dropped as dishonest.** Probe history was going to be a fourth bundle key, but `report_runtime_probes` is the sole writer of `self.runtime_probes` and had no caller, so the key had never appeared in a bundle and folding it would have folded a structurally-always-empty value. Dropped instead, with a register row for the pipeline as a whole (below).

**The guard is now a hard gate** (`scripts/validate_architecture.py`). It asks both questions — undeclared, and declared-but-unreferenced — and excludes `rpc-routes.ts` from its own haystack so a route row can never vouch for itself. Opt-out is an inline `# no-frontend-caller: <reason>` marker at the definition, scanned through the whole contiguous comment block above the `def` so a real explanation can span lines. The marker is named for exactly what the check tests, so it stays honest whether the reason is "only the launcher calls this" or "dead, tracked by register 4a" — the five survivors carry the latter. The exemption count prints on every clean run, so the set cannot grow quietly, which is the failure mode of any allowlist.

**Two things the on-device validation did *not* cover, recorded so they are not mistaken for verified.** The `config_validation` block was exercised only on a *valid* config (`error_count: 0`), because the dev machine's config is well-formed; the populated-with-errors path — including the `safe_message` redaction that matters most — is covered by unit test (`test_support_bundle_rpc.py::test_config_validation_never_carries_the_offending_value` and `test_config_validator_safe_message.py`) rather than by a real bundle. And the `edge_not_installed` reactive path (§1.2's justification for deleting `is_edge_installed`) is untestable on a host with Edge present, which this one is; the path was verified intact in the shipped bundle and in all four browser-auth stores, not triggered.

### 1.3 Event-bus mismatches

~~Three dead handlers and seven unconsumed events.~~ **RESOLVED — one line of this section was wrong, one was stale, and the two highest-impact defects were not in it.** Re-derived by cross-referencing every `Events` member against emit sites, `@subscribe`, frontend subscriptions in both constant and string form, `src/types/events.ts`, and `WATCHED_EVENTS` — handling indirect emitters (`_emit_down`/`_emit_up`, `audit_emitter`, `wrapper_signals`) that a naive `Events.X` grep misses.

**Subscribed but never emitted (dead handlers):**

- ~~`SUSPEND`/`RESUME`~~ **RESOLVED — and this was the one item here that wrote bad data to a third party.** The finding held (subscribed at `playtime/service.py:274,286`, no emitter, and no suspend detection of any kind exists in the tree — no logind listener, no SteamClient hook), but it understated the consequence. `_provisional_duration` was `wall_clock − total_sleep_secs` and the sleep total was permanently `0`, so **suspending the Deck mid-game billed the entire suspend as playtime**: put a game down at 23:00 without quitting, wake at 08:00, get a 9-hour session. That value reached `play_sessions`, `game_stats.total_secs` and the streak columns — and `PlaytimeSyncService` **pushed it to GOG and Epic**, where it cannot be retracted.

  Fix: not an emitter. `_provisional_duration` now measures awake time off `time.monotonic()` — `CLOCK_MONOTONIC` does not advance across suspend on Linux — so sleep is excluded with no signal at all, including on a hard suspend that would fire none. `started_at` stays wall-clock because `_update_daily_stats` needs a real date for day attribution. Both enum members retired; `total_sleep_secs`/`suspended_at` deleted. `tests/unit/test_playtime_suspend_accounting.py` simulates the gap by advancing the wall clock without advancing the monotonic clock, which is exactly what a real suspend does to a live process.

- `ARTWORK_REQUEST`: confirmed — subscribed `artwork/event_handlers.py:133`, never emitted, ever. **Kept deliberately** as the entry point for a force-refetch trigger (the `force=True` arm exists for the account-switch case) and marked `# unwired:`. The two artwork paths that do run reach ArtworkService by other routes.

- ~~`SHORTCUT_CREATED`~~ **RESOLVED by making the handler live, not by deleting it.** The finding held, but "the auth-shortcut-artwork feature is dead" overstated it — per §1.1.1's lesson, most of that subscriber's job was already done elsewhere. The handler only acts on `is_auth=True`, and of the six stores: Ubisoft has its own live artwork path (`ubisoft/auth/context.py:40`), and Epic/GOG/Amazon/Microsoft were migrated to ephemeral 15-second shortcuts (`_self_heal_auth_shortcuts` deletes their old persistent rows). The single real gap was **Battle.net**, the one store that both reaches `shared/auth_shortcut.py` and keeps a persistent tile — so its "Battle.net" sign-in tile rendered bare in the library.

  Fix: `ensure_auth_shortcut` now emits on its create branch only (not the already-in-VDF branch, which would re-run the SGDB lookup on every sign-in). The subscriber, the `_AUTH_TITLE_FOR_LOOKUP` mapping and the `CANONICAL_SCHEMA` contract already existed and already agreed — only the emit was missing. Guarded by driving the **real** `ArtworkService._on_shortcut_created` with whatever the emitter actually sent and asserting on the SGDB call, rather than against a hand-written payload: §1.1.1 shipped twice because both guards there pinned opposite halves of a mismatch.

**Emitted but never consumed:**

- ~~`TOAST_NOTIFICATION`~~ **RESOLVED (item #2)** — retired; its three emitters now use `LAUNCHER_STAGE`.
- `CIRCUIT_STATE_CHANGED`: confirmed no subscriber — **but this section missed the part that matters.** The enum docstring documented a payload that has never existed: it claimed `game_key`, `state`, `recent_count`, `failure_kinds`, while the emit site (`launch_history/service.py:110`) sends `store`, `game_id`, `is_open`, `failure_count`. `CANONICAL_SCHEMA` carried the real set, so the gate stayed green while the prose lied unchecked. The trigger values were wrong too (really `record_failure_<kind>`, `clear_failures`, `arm_bypass`, `closed`). Register **4a** exists to build the `useCircuitState` hook from that docstring and would have read `undefined` for four of five keys — the `app_id`/`game_id` failure of §1.1.1, repeated inside the fix for §1.1.2's silent failure. Docstring corrected against the emit site; the missing subscriber stays with 4a, now marked `# unwired:`.
- ~~`STORE_REGISTERED`~~ **This finding was wrong.** There *is* a live consumer: `src/stores/store-info-store.ts:46` subscribes and refetches store infos, and the boot-time emit reaches it through the replay buffer on the first poll. Only the enum docstring's "Consumed by metrics_collector.py" was false. Docstring corrected; no code change.
- ~~`STORE_ERROR`~~ **RESOLVED — retired, and it was worse than recorded.** Not merely unemitted today: `git log -S store_error -- py_modules/` reaches the initial commit and finds no emitter ever. The emitting half was never built while the frontend half sat there looking wired. Verified before deleting that every failure it could carry is already covered — a per-store sync failure logs, emits `SYNC_FAILED` and toasts via `LAUNCHER_STAGE` (`sync_run_mixin.py:389`); an auth failure logs, emits `STORE_AUTH_FAILED` and flips the store's frontend status (`store_registry.py:340`); and the `StoreError` *exception* is raised only inside `StoreBase._run_cli`, which §3.2 confirms is dead. Enum member, `events.ts` row, `WATCHED_EVENTS` row, frontend handler and the `toasts.storeError` string in all 16 locales all deleted.

- ~~`SUBSCRIPTION_DETECTED`/`_EXPIRED`/`_CHECK_FAILED`~~ **RESOLVED — retired.** They were missing **three** legs, not one: no Python subscriber, absent from `src/types/events.ts`, and absent from `WATCHED_EVENTS`, so the frontend never even polled for them. ### 2.9 The launch-options parser is not dead code, it is an unfinished feature

Split out of §2.8, whose bullet reads "`parse_launch_options` — dead, imported nowhere". Nothing imports it, and every other implication of that sentence is wrong. Found by looking for *replicated* logic before deleting, which is the only reason it was caught.

**The module is entirely unimported, not just that one function.** `launcher/types/options.py` is 198 lines with zero importers; `launcher/types/__init__.py` is empty, so nothing re-exports it; and `apply_lsfg_env`, which looked like the live half, has no external caller either. Vulture runs as a **hard** gate over `py_modules/unifideck` and did not catch it, because `min_confidence = 80` reports unused imports and variables but not unused functions or whole unimported modules. That threshold is its own finding.

**Its destination, however, is fully built and consumed in eleven places.** `ParsedOptions`'s fields are mirrored exactly by live dataclass fields that nothing ever writes:

| Field | Consumers | Written by |
|---|---|---|
| `LaunchContext.env_overrides` | `helpers.py:94` and `proton/infrastructure/core.py:384`, both `env.update(...)` applied **last** so a user value beats the plugin's compat env — and covered by `test_proton_prepare_store_env.py:207` | nothing |
| `RuntimeState.wrappers` | 6: `helpers.py:119` (native argv), `generic.py:67`/`:91`, `epic.py:265`, `epic_launch_params.py:207`, `gog.py:295` | nothing |
| `RuntimeState.game_args` | 5: `helpers.py:142`, `generic.py:74`/`:97`, `epic.py:302`, `gog.py:298` | nothing |
| `RuntimeState.lsfg_requested` | none | nothing |

`LaunchContext.raw_options` *is* populated, at all four dispatcher construction sites. `RuntimeState.to_log_dict` already reports `wrappers_count`, `game_args_count` and `lsfg_requested`. Tests already build state with wrappers and args, one of them named `test_wrappers_and_game_args_are_preserved`. And `prepare_windows_plan` returns `tuple[Any, Any]` whose second element is always `None`, with `helpers.py:323` commenting "parsed_options reserved for LSFG/wrapper parsing" and `orchestrator.py:34` documenting an "options" step that never runs. The feature is roughly 90% built and missing one call.

**It is also promised to users.** `docs/launch-options.md:106-127` has a "Planned / not yet wired" section naming this file and specifying the syntax for wrapper words, game args after `%command%`, and LSFG. Deleting the module would silently convert a documented "planned" feature into a removed one.

**There is genuine duplication, and it is not where the audit looked.** Four handlers parse a Steam launch-options string, three of them live:

| Where | Job | Status |
|---|---|---|
| `services/shortcut/launch_options.py` | regex-extract `store:id`; `preserve_user_params` swaps our core, keeping theirs | live (sync/reconcile) |
| `steam-bridge/wrapper-shortcut-launch.ts` `extractUserParams` | strip our tokens, keep user `mangohud`/`gamemoderun`/`#%command%` | live (frontend) |
| `launcher/dispatcher.py:41` `_promote_env_tokens` | promote `UNIFIDECK_*` `KEY=value` from argv into `os.environ` | live (launch hot path) |
| `launcher/types/options.py` | shlex tokenize, all env vars, LSFG overlay, `%command%` split | the missing call |

`_promote_env_tokens` is a 12-line reimplementation of `_tokenize_options` + `_split_env_overrides`, deliberately narrower (only `UNIFIDECK_*`, `setdefault`, never overwrite) but splitting with a naive `raw.split()` where the dead one uses `shlex.split`. No live collision today, because `stores/ubisoft/auth/shortcut.py:33-34` and `buildTemporaryLaunchOptions` both emit space-free unquoted values, but the frontend's `extractUserParams` regex already anticipates quoted values, so it is a latent corruption. The other two are *not* duplicates: they work on different data in different processes and directions, and `is_unifideck_owned` already consumes the first as an injected callback, which is the right shape.

Note also that env-var passthrough works today **without** the plugin: Steam sets `VAR=value %command%` vars itself and the launcher inherits them, which is why the parser was never needed for that half and why its absence went unnoticed.

**Two hazards to handle when wiring it:**

- **`env_overrides` is doing double duty.** `service.py:214` reads `float(ctx.env_overrides.get("started_at", "0"))` from it as a dispatcher-to-service data channel, while two other call sites splat the same dict into the game's environment. Nothing populates it today, so that read is dead and `started_at` is always `0.0` despite a docstring claiming it is "passed in by the dispatcher". A lowercase key cannot arrive from parsing (`_ENV_TOKEN_RE` is uppercase-only), so wiring does not collide, but `started_at` wants its own field rather than growing the overload.
- **Wiring makes `ctx.env_overrides` non-empty for the first time.** That is the feature and its main risk: both consumers apply it *last*, specifically so a user value overrides the plugin's own compat env. `ge-proton11-3-builtin-icuuc-stub` and `ld-library-path-leak-umu-127-libz` are both recorded incidents where that env's precision was load-bearing.

**PARTIALLY RESOLVED 2026-08-25. The env half is wired; the wrapper half was stopped by a measurement taken while wiring it.**

What shipped:

- **`ctx.env_overrides` is populated**, at all four dispatcher construction sites, so a user's `KEY=value` token now reaches the game's environment. Both consumers already applied it last, and `test_proton_prepare_store_env.py:207` already asserted that ordering, so this needed no change to either env builder.
- **LSFG works**, by merging `apply_lsfg_env`'s overlay *under* the user's explicit tokens in the same dict. Putting it there rather than in the env builders is what let both the native and Proton paths pick it up without either growing a parameter. `RuntimeState.lsfg_requested` finally has a writer.
- **The duplicated tokenizer is merged.** `_promote_env_tokens` now splits with the parser's `tokenize_options` (shlex) instead of its own `raw.split()`, so `KEY="a b"` stops promoting a truncated value. Its narrow policy (`UNIFIDECK_*` only, `setdefault`) was deliberate and is unchanged; only the splitting was duplicated. `_tokenize_options` was renamed public for the second consumer.
- **The reserved return slot is gone.** `prepare_windows_plan` returns the plan, properly typed `ProtonLaunchPlan` instead of `tuple[Any, Any]`, and the three call sites plus `orchestrator.py:34`'s "options" claim are updated.
- **The `started_at` overload is gone.** `_build_runtime_state` no longer reads an internal timestamp out of a now-user-controlled dict. It never worked (nothing populated it, nothing read it, and `_launch_started_at` is the real clock), and leaving it would have been a genuine trap.
- **`dispatcher.py` hit the 550-LOC cap** at 584 and was split, not allowlisted: the three functions that interpret the argv tail moved to a new `launcher/argv_options.py`, taking it to 513.

**What was stopped, and why.** `state.wrappers` and `state.game_args` are still unpopulated. `parse_launch_options` was written for a full Steam `LaunchOptions` string, where `%command%` separates wrapper words from game arguments. The dispatcher receives the **post-expansion argv tail** (`" ".join(argv[2:])`), which frequently has no `%command%` left in it, and the parser's fallback for that case moves *every* bare token into `game_args`. Since every argv builder does `argv.extend(state.game_args)`, and the frontend's own `extractUserParams` deliberately preserves the user's `mangohud`/`gamemoderun` into the temp-shortcut options, wiring it produced this:

```
argv tail : UNIFIDECK_UBISOFT_ACTION=auth mangohud gamemoderun
wrappers  : []
game_args : ['mangohud', 'gamemoderun']   ← appended to the GAME's argv
```

That is a launch-breaking regression on exactly the feature the wiring was meant to deliver. Left empty, which is what every release so far shipped. `tests/unit/test_launch_options_wiring.py` pins both halves, so re-wiring it is a deliberate act against a red test, and the worked example above is a test of its own.

#### What Steam actually passes — measured, 2026-08-25

The first write-up of this section said the deciding fact "was not established". It is now, on this Steam Deck, with a logging script as a non-Steam shortcut's `Exe`, driven through `SteamClient.Apps.SetShortcutLaunchOptions` + `RunGame` over CDP. Probe shortcut added and removed per run; `shortcuts.vdf` back to its original 1264 entries.

| `LaunchOptions` | argv the Exe receives | env set by Steam |
|---|---|---|
| `probe-a probe-b` | `[probe-a, probe-b]` | none |
| `PROBE_ENV_A=1 %command%` | `[]` (argc=0) | `PROBE_ENV_A=1` |
| `PROBE_ENV_A=9 %command% tail1` | `[tail1]` | `PROBE_ENV_A=9` |
| `epic:Salt PROBE_ENV_B=2` | `[epic:Salt, PROBE_ENV_B=2]` | **none — not set** |
| `env %command% epic:Salt` | `[epic:Salt]`, under `env` | none (the wrapper ran) |
| `%command% after1 after2` | **never launched** (2 of 2 attempts) | — |
| `ubisoft:upc-auth UNIFIDECK_UBISOFT_ACTION=auth mangohud gamemoderun` | `[ubisoft:upc-auth, UNIFIDECK_UBISOFT_ACTION=auth, mangohud, gamemoderun]` | none |

Four things follow, and they settle the design question rather than restating it:

1. **`%command%` is honoured for non-Steam shortcuts.** Assignments before it are exported by Steam and stripped from argv; tokens after it arrive as argv.
2. **A wrapper word before `%command%` is executed by Steam itself.** `env %command% epic:Salt` ran the probe *under* `env` and still delivered `argv[1] = epic:Salt`. So `mangohud %command% epic:Salt` already works today and needs no plugin code. **`ParsedOptions.wrappers` is therefore not "deferred" but unreachable through this path**: wrapping is a pre-exec act, and by the time our launcher has a `argv` there is nothing left to wrap. `RuntimeState.wrappers` is read by six argv builders that can only ever prepend an empty list. That is phantom vocabulary in the §2.8 sense, and it should be deleted rather than wired — see item 23b.
3. **An assignment *after* the game key is NOT exported by Steam** (`PROBE_ENV_B` arrived as argv and was unset in the environment). Nothing but the launcher can apply it, and before this pass nothing did. So the env half that shipped is a genuinely new capability, not a re-plumbing of something Steam already did.
4. **The `game_args` hazard reproduced exactly**, on the frontend's own temp-shortcut shape (last row). `mangohud` and `gamemoderun` really do arrive in the tail, so populating `game_args` from it really would have passed them to the game. Worth noting they are *useless* there per finding 2, which makes `extractUserParams` preserving them into the tail its own small bug.

One user-facing trap found in passing: **`LaunchOptions` that begin with `%command%` did not launch at all**, twice, while the same string with any token in front of it launched fine. Not chased further, and not caused by this change.

#### Validated by launching a real game, 2026-08-26

Run against `gog:1207658924` (The Witcher: Enhanced Edition, the one installed title on this Deck), driven through `RunGame`, with the evidence read out of `/proc/<pid>/environ` of the **game process itself** rather than from a log line.

| Scenario | `LaunchOptions` | Result |
|---|---|---|
| Baseline (the regression guard) | `gog:1207658924` | Launched to `launcher.exe`, correct per-game prefix, none of the probe variables present |
| User env override | `gog:1207658924 MY_PROBE_VAR=hello WINEDLLOVERRIDES=…` | Both present **on the game process**. `WINEDLLOVERRIDES` arrived with the user's entry first and Proton's appended after it |
| LSFG | `gog:1207658924 LSFG=1` | `ENABLE_LSFG=1` plus all three exports from the real `~/lsfg` (`LSFG_PROCESS=decky-lsfg-vk`, `ENABLE_GAMESCOPE_WSI=0`, `DXVK_HDR=0`) present on the game process |
| LSFG, alternate flag | `gog:1207658924 ENABLE_LSFG=1` | Same overlay, without the bare `LSFG` token. Correct |
| Steam's own env form | `MY_STEAM_VAR=viasteam %command% gog:1207658924` | Game launched, variable **absent from the game** |
| Quoted value (after the `shlex.join` fix, re-run on the deployed build) | `gog:1207658924 MY_QUOTED="alpha beta" LSFG=1` | `MY_QUOTED=alpha beta` intact on the game — it was `alpha` before the fix — with the LSFG overlay alongside |

**That last row is a finding, and it inverts what the docs said.** `docs/launch-options.md` presented `VAR=value %command%` as the mechanism that "works today". It does not, for a Unifideck game that runs under a forced Proton. Steam really does export it — it is present on the outer `steam-runtime-launch-client` process — but the launch then goes through `container_escape`, and `_forwarded_env` (`container_escape.py:143-158`) forwards a variable only when it is in `_ALWAYS_FORWARD` or its value **differs from `os.environ`**. That rule exists to stop container values (notably `PATH`) leaking back, and it is right to have. Its side effect is that a variable Steam exported is byte-identical to the inherited environment and gets dropped with it.

Confirmed in isolation rather than inferred:

```
Steam-set var (equals os.environ)      -> forwarded: False
launch-options var (explicit mutation) -> forwarded: True
ENABLE_LSFG   (explicit mutation)      -> forwarded: True
```

So the route wired in this pass is not a second way to do the same thing, it is the **only** reliable one, and the doc now says so with the measurement attached. The `%command%` form still works for wrapper *programs*, which Steam applies before the escape ever happens.

Not fixed here: making Steam-exported variables survive the escape would need a way to tell a user's variable from container junk, and `_forwarded_env` deliberately has none. Recorded as item 25.

`docs/launch-options.md` now documents the env and LSFG routes under "What works today", and lists wrapper words and game arguments under "Not supported" with the reason, rather than promising them as "planned". The stale "DEAD CODE" note in the `launcher.md` skill is corrected.

**Two lessons.**

*"Imported nowhere" is a fact about the module, not a verdict on the feature.* Before deleting, check whether the destination is built and whether a user-facing doc promises it. This one had eleven live consumers, a reserved return slot, passing tests, and a documented syntax, and the register had it down as one dead function.

*And the converse: code being unreached is sometimes load-bearing.* The parser's `%command%` assumption was silently wrong for its own call site, and nothing revealed that until it ran. Wiring dead code is a behaviour change, so it needs the same measurement a fix does; the fallback branch here would have shipped as a regression on the strength of the code "already being written and tested".

## Part 3 — Store logic drift and redundancy

### 3.1 The wrapper/CLI distinction is two hand-maintained tables with no link

- Canonical wrapper identity is a string frozenset in `launcher/wrapper_stores.py:37`: `WRAPPER_STORES = {"ubisoft", "battlenet"}` with predicates `is_wrapper_store`, `prefix_owns_game_install`, `skips_generic_compat`, `uses_manual_download_phase`.

The predicates were deliberately separated ("EA App will be a wrapper store that does not own its installs"), which is sound reasoning, but the identity source-of-truth is still split across `launcher/` and six `store_info` descriptors. `scripts/validate_architecture.py` now machine-checks the `uses_wine ↔ WRAPPER_STORES` agreement.

**RESOLVED 2026-08-26 — the mechanism held, the consequence was wrong, the prescribed remedy was impossible, and the hazard that mattered was the inverse of the one recorded.** Both tables existed as described. Everything that follows from that in this section does not.

- **`uses_wine` had zero readers.** Not in `py_modules/`, `src/`, `bin/`, `tests/` or `docs/` — no attribute access, no dict key, no `getattr`. The frontend's own `StoreInfo` interface (`src/types/api.ts:153`) does not declare it, and the only two fields anything in `src/` reads off that payload are `name` and `display_name`. So the drift this section warns about could not change behaviour in either direction: the two tables were not a source of truth and a copy, they were a source of truth and an echo. §1.1.4's lesson exactly — right mechanism, wrong named consequence.
- **This section's own closing line was stale when it was written.** Check 3 was already a hard gate. It was enforcing agreement on a value nothing read, which is worse than not enforcing it: the presence of a green check is what made the pair look handled.
- **The prescribed remedy (register item 7, "derive the wrapper predicates from a single `store_info` field") is not implementable in that direction.** `wrapper_stores.py` is imported by `launcher/types/context.py` and runs under the system Python (3.10–3.14) in the out-of-process launcher; `test_module_is_stdlib_only` asserts it has zero imports. It cannot read `store_info`. Only the reverse works.
- **`vulture_whitelist.py:126` carried a false justification** — "StoreInfo fields are read through attribute access by every store". Untrue for this member, and the reason a dead-code pass would have skipped it. The same phantom-justification shape as §1.2's DiagnosticsPanel docstrings, in the one file whose job is recording why something *looks* dead.

**The hazard this section missed, and it is the inverse of the one it recorded.** `tests/unit/test_wrapper_stores.py:32-37` parametrized over `WRAPPER_STORES` and asserted **all four** predicates True; line 115 did the same for the prefix-reset guard. Renamed because the old name did not describe what the gate checked — "Windows-only stores running under Proton/Wine" reads as true for Epic/GOG/Amazon Windows games too, so a maintainer setting Epic's `uses_wine=True` would have been told they were wrong by a check whose reasoning was nowhere on the page.

Check 3 keeps its `StoreInfo.name == directory` arm and loses the `uses_wine` arm, which is now unfailable. Per §2.1's lesson, the durable fix deletes every copy but the one a machine checks; here the machine check became unnecessary because the copy became impossible.

The tests are unwelded onto an explicit `_EXPECTED` table with one row per wrapper store and a guard asserting `set(_EXPECTED) == WRAPPER_STORES`, so a new store must state its own answers rather than inherit them. The four unpinned dispatch sites are now covered. **Verified against planted violations, not only against a clean tree** (§1.1.4). Adding `"eaapp"` to `WRAPPER_STORES` alone now fails 11 tests plus check 9, naming every site that needs a row; before, it failed the two welded predicate tests and `_SPECS`, and the obvious way to green them was to add the store to both frozensets. **Lesson: a checked duplicate is not a linked one, and a green gate on a dead value is worse than no gate.** This pair had a hard CI check, which is exactly why nobody asked whether either side was read. ### 3.2 CLI-store drift (Epic = reference, GOG diverges, Amazon partial)

`shared/cli_install_helpers.py` exists to unify CLI stores but is consumed by only 2 of 3.

- **Binary resolution 2-of-3 break**: Epic and Amazon declare a `CLITool` descriptor and resolve via `StoreBase._find_binary` → `binary_resolver`. GOG hardcodes `bin/gogdl` in `_resolve_gogdl_bin` (`gog/store.py:476-494`), bypassing the resolver, its version check, and its multi-path search.
- **Subprocess/output 2-of-3 break**: Epic and Amazon use `drain_install_output`/`TailRingBuffer`/`wait_with_timeout`. GOG reimplements its own `_read_progress_loop`, two-phase stall watchdog, and `_terminate_gogdl` in `gog/install/progress.py`.
- **Three ETA parsers, three speed parsers, near-verbatim copies**: `shared/cli_install_helpers.py:196/219` (Epic only), `gog/install/progress.py:275/296`, `amazon/amazon_progress.py:23/44`. `amazon_progress.py`'s own docstring admits it was "kept store-local rather than folded into shared" because the shared versions are "close but not byte-identical."
- **Cancellation**: only Epic uses shared `terminate_process_tree`. Amazon re-raises without killing the tree; GOG uses its own `terminate(); sleep(1); kill()`.
- **`StoreBase._run_cli` is dead code** (`store_base.py:161-211`): defined, never called. Every CLI store inlines `asyncio.create_subprocess_exec` instead.
- **Auth/token idioms diverge**: Epic/Amazon share near-identical `_check_*_authenticated` `user.json` readers; GOG and Microsoft instead have full `tokens/` manager subpackages (structurally parallel but not in `shared/`).

**RESOLVED 2026-08-26. One bullet was inverted, one understated a UI hang, and the two costliest defects were not in the section at all.** Every bullet was re-derived against the tree before being worked, per §1.3's lesson, and the cancellation and stall claims were **measured** against the real store code rather than grepped. Verdicts in the original order.

- ~~**Binary resolution 2-of-3 break**~~ **RESOLVED — the mechanism held, the named benefit was phantom, and the real losses were not listed.** GOG did hardcode `bin/gogdl`, `is_file()`-check it and return the path *anyway* on failure. But "bypassing the resolver, **its version check**" names something that does not exist for any store: `BinaryResolver.check_version` has **zero callers** in the tree and `CLITool.min_version` is never compared to anything, so Epic and Amazon get no version check either. What GOG actually lost was (a) the **SHA256 check** — `_log_signature_mismatch` runs only on the resolver's Tier-1 hit, so the `gogdl` entry sitting in `_KNOWN_HASHES` was never compared against anything, and a half-applied update read as "GOG is broken"; (b) the **executable-bit test**, where `_is_executable` skips a file whose exec bit was lost in transit and `is_file()` does not — the exact case `scripts/ensure_executable_bits.py` exists for; and (c) Tier 2/3 fallback.

  **The compounding half was also absent from the bullet.** `GOGStore.is_available` gated on tokens and a userdata probe and never on the binary, so a broken gogdl left GOG showing **connected** — the library syncs fine, being pure HTTP — while every install died at spawn with a raw `OSError` string in the download row. Epic and Amazon both go disconnected, and Amazon additionally converts a spawn failure into a typed outcome. Fixed all three: `GOGStore.CLI_TOOL` + `_find_binary`, an availability gate, and an `OSError` arm around the spawn.

- ~~**Subprocess/output 2-of-3 break**~~ **INVERTED — acting on this as written would have been a regression, and register item 6 said to.** GOG's `_read_progress_loop` is not a reimplementation of `drain_install_output`; it is a **superset**, carrying a two-phase stall watchdog that the shared helper never had. Measured: `drain_install_output` awaited `readline()` with no timeout at all, and `wait_with_timeout` runs only *after* EOF — so a child that is silent for 5s with stdout open returns from the drain at 5s under a 2s envelope timeout. Epic's 7200s and Amazon's 3600s install caps are therefore **unreachable while the CLI holds stdout open**, and since `max_concurrent` defaults to 1, one wedged install blocked every queued game until `plugin_loader` was restarted. That is the class behind `install-hang-orphaned-wineserver-lock` and `install-stuck-broken-proton-experimental-hang`.

  So the drift direction is **up, not down**. Lifted GOG's shape into `drain_install_output` (`stall_s` / `finalize_s` / `in_finalize`); GOG keeps its behaviour through the shared helper, Epic and Amazon gain stall detection they never had. The helper raises `InstallStalledError` rather than killing, so each store keeps exactly one `terminate_process_tree` site instead of two that can drift. **Do not re-file this as "make GOG consume the shared helpers".**

- ~~**Three ETA parsers, three speed parsers**~~ **RESOLVED — and the docstring reason not to unify describes an unreachable divergence.** `amazon_progress.py` declined to fold in because the shared versions were "close but not byte-identical … (nile's sign handling differs)". Measured over 23 vectors of real legendary/gogdl/nile output: **the three ETA parsers are identical on every vector, and the three speed parsers agree on every real CLI line.** They diverge only on `+ Download -9.75 MiB/s` (unspaced sign) and `Download 5.00 MiB/s` (no `+`), neither of which any of the three CLIs emits.

  One real defect fell out of the diff: shared and GOG returned a **negative** transfer rate for the unspaced form, which would render as a negative MB/s. Amazon's `lstrip("-")` was the only correct one of the three and is the one kept. Also merged the transfer-line parser itself: gogdl and nile emit the *same* `Progress: <pct> <written>/<total> … ETA:` line, so the two store copies were one function all along. `amazon_progress.py` deleted (89 lines); `parse_progress_line` renamed `parse_percent_re`, because Amazon was importing two different functions of that name and aliasing one at the import, which is a large part of why the duplication went unnoticed. `tests/unit/test_cli_progress_parsers_agree.py` pins the vector table so the equivalence claim stays checked rather than remembered.

- ~~**Cancellation**~~ **RESOLVED — this was the highest-value item in §3.2 and the register understated it by a wide margin.** "Amazon re-raises without killing the tree; GOG uses its own `terminate(); sleep(1); kill()`" is mechanically right and reads like tidy-up. Measured, driving the real store code against a live child that forks a worker, with Epic as the control:

  ```
  EPIC   : tree [37444, 37445] -> after cancel, ALIVE: []            clean, 0.00s
  GOG    : tree [37357, 37358] -> after cancel, ALIVE: [37357,37358] *** LEAKED ***
  AMAZON : tree [37390, 37391] -> after cancel, ALIVE: [37390,37391] *** LEAKED ***
           cancel STILL BLOCKED after 6s   (bound is _install_timeout = 3600s)
  ```

  **What the user experienced.** Press Cancel; the row flips to Cancelled; the download tool keeps running — parent *and* its `multiprocessing` workers (gogdl spawns `Process` in `dl/workers/task_executor.py`; nile is a PyInstaller ELF carrying `multiprocessing`). So bytes keep landing after "cancelled" and free space keeps falling with no visible download; a cancel-then-uninstall deletes a directory another process is still writing into, and files reappear after the uninstall reports success; an orphan can still write the completion manifest, the exact shape `launcher/wrapper_prefix_probe.py:22` records for Battle.net; gogdl leaks a `/dev/shm` segment per orphan; and a retry runs a second downloader over the same directory. GOG's own `_terminate_gogdl` could not have helped even when reached: it killed the parent only, and its `await asyncio.sleep(1)` is skipped outright in a task already being cancelled — the precise failure `terminate_process_tree`'s docstring documents and guards with `contextlib.suppress`.

  **Amazon's second defect was not in the register at all: cancelling hung the UI.** It caught `CancelledError` into `drain_exc`, then ran `wait_with_timeout(proc, 3600)` *before* re-raising. `DownloadService.cancel` awaits the task and the RPC awaits `cancel`, so the whole call blocked until nile finished or an hour elapsed. Epic has had the same two steps in the opposite order the whole time. Fixed by transposing them — the leak and the hang are **one** bug, not two.

- ~~**`StoreBase._run_cli` is dead code**~~ **RESOLVED — deleted (register item 10).** Zero callers confirmed; `stores/shared/cli_credentials.py:21` already documented it as dead. Deleted rather than adopted: every CLI store needs to *stream* stdout for progress, which a collect-at-the-end helper cannot do, so adopting it would have meant rewriting it anyway. A comment in its place says so, and points at `core.binaries.clean_cli_env` for the one thing it did provide. **Note a claim this bullet invites that is wrong:** bypassing `_run_cli` did **not** leave GOG with an unscrubbed environment — every GOG subprocess site goes through `acquire_gogdl_creds` → `clean_cli_env` (`gog/tokens/gogdl_credentials.py:84`). No change was needed there.

- ~~**Auth/token idioms diverge**~~ **RESOLVED for the `user.json` half; the `tokens/` half was already closed.** The two readers were ~35 structurally identical lines differing in exactly three places — the store label, the config key, and the final predicate — now `stores/shared/cli_credentials.read_cli_user_json`. The risk is a change to one copy and not the other, which has already happened once: `nile` is pinned at 1.1.2 precisely because 1.2.0 deletes the `user.json` the Amazon copy reads, and nothing structural connected that constraint to Epic's identical reader. Sharing also gained Amazon an object check it lacked — it called `data.get` on whatever `json.load` returned, so a `user.json` holding a JSON *array* raised `AttributeError` out of the store-status path. The GOG/Microsoft `tokens/` half of this bullet is largely stale: register item 9 already extracted `security/token_file.EncryptedTokenFile` and both consume it. What remains is package *shape*, not duplicated logic.

**Found while resolving this section, not in the register:**

- **A failed GOG install never said why** *(highest user-facing impact in §3.2)*. Epic and Amazon fold the CLI's output tail into the error (`legendary_exit_1: …`, `nile_exit_1: …`) — both were deliberate fixes for reported silent failures (`ud026-epic-install-error-surfacing-and-dlc-fallback`, `amazon-nile-exit-1-error-surfacing`). Fixed with a `gogdl_exit_{rc}: {tail}` outcome — `EXIT_PREFIX_RE` in `src/lib/download-errors.ts` has stripped exactly that prefix all along and its docstring cites `gogdl_exit_2:` as an example, a format nothing in the tree ever emitted (phantom vocabulary in the §2.8 sense, on the frontend). ### 3.3 Wrapper-store drift (Ubisoft mature, Battle.net consumes shared, half-migrated)

~~Ubisoft keeps a private duplicate of what Battle.net gets from `shared/`; migrate it.~~ **RESOLVED — the observations mostly held, the remediation did not, and the two highest-value defects were not in the section.** Re-derived from the tree before being worked, per §1.3's lesson. Of the three migrations register item 8 named, **one was partly right, one was blocked on data nobody had measured, and one is now declined on the record.**

**The one list that was entirely correct** is what is genuinely shared: `wrapper_install`, `prefix_placement`, `wrapper_auth_monitor`, `installed_size.dir_size_bytes` and `wine_path` each have a live consumer in both stores. Verified by import graph.

**Prefix cloning — one of three claims was wrong, and acting on it would have deleted a repair path.**

- `rsync_clone` **was** a real duplicate, and the copy was missing the flag that matters. `shared/prefix_clone.rsync_clone` takes `checksum=`, and says why: *"Required when repairing an existing prefix: identity files are small and are frequently rewritten within the same second at the same length, so the quick check skips them and the repair silently does nothing."* Ubisoft's copy had no such parameter, and **three of its five call sites write into a tree that may already be populated** — including `prefix/manager.py`'s game-prefix identity repair, the one clone that can *never* delete its destination first because the game's files live inside the prefix. Both docstrings now say so, so neither reads as dead beside the other. The §1.4 `resolve_proton_path` shape inverted: there two same-named functions really were incompatible, here two differently-named ones were filed as duplicates because they touch the same file.
